# ReviewForge v4.2：从教材式说明转为批判性综述

本升级针对“每小节只有定义、公式和几句优缺点”的问题。目标是让每个核心小节围绕科学问题，比较具体研究，解释证据差异，并形成有边界的结论。

这不是自动加长正文。篇幅、段落数、引用数、得分和公式数量都不能单独证明综述深度。

## 一、哪些内容发生变化

| 环节 | 旧流程容易出现的问题 | 新要求 |
|---|---|---|
| 小节设计 | 按标题解释概念 | 先写问题、待检验观点、比较维度和段落任务 |
| 证据阅读 | 一条短摘录被用于支撑整段 | 提取比较所需的研究字段，每个支持性字段有位置和摘录 |
| 正文组织 | 每篇文献各讲几句 | 围绕问题比较研究之间的关系 |
| 生成粒度 | 按字符数切块，论证被割断 | 以完整 subsection 为单位，保留其全部下级标题 |
| 审稿 | 主要检查格式、引用、明显错误 | 加入问题回答、比较、解释、证据范围和结论的整节审查 |
| 风格校准 | 全稿写完才发现不满意 | 先写一个有代表性的困难小节，记录作者对该版本的反馈 |
| 成稿处理 | 局部通过就直接覆盖主稿 | 单独保存候选稿，先核查整章连贯性，再明确整合 |

## 二、与原续跑命令的关系

`resume_review_v4.bat` 仍执行原有分块断点流程。升级 skill 不会把一个正在运行的 Python 进程改成新架构，也不会自动改变旧审稿结果。

新流程的入口是：

```powershell
python .\synthesis_pipeline.py init --workspace .\workspace
python .\synthesis_pipeline.py audit --workspace .\workspace
python .\synthesis_pipeline.py revise --workspace .\workspace --unit unit_002
```

最后一行的 `unit_002` 只是格式示例，实际选择应以生成的计划为准。
`init`、`audit` 不调用模型。`revise` 使用现有 API 配置，会发生模型请求。
不要在旧程序持续改写同一份 `review_en.tex` 时对其开展新候选稿审查；先等它结束，或把稿件和需要的证据复制到单独工作区。

本次升级不会自动执行上述改写命令，不会重置旧运行状态，不会把新稿强行写入英文主稿或中文主稿。

## 三、初始化只建立待填写设计

运行 `init` 会读取当前 `review_en.tex`，生成：

- `synthesis_plan.json`：每个完整小节的论证设计，绑定稿件和小节的 SHA-256；
- `study_comparisons.json`：该稿件引用文献的比较字段模板。

核心内容默认留空。模板存在不等于设计通过；不得把标题自动复制到所有字段冒充设计。
发现已有这两个文件时程序拒绝覆盖。稿件结构变化后，应对照新旧版本重新映射并更新设计，不能只改哈希绕过校验。

完整小节的识别规则：每个 `subsection` 连同其全部 `subsubsection` 和 `paragraph` 子标题一起处理；顶层 section 下未归属某个 subsection 的引言独立处理。标题本身没有正文时不会被伪装成一个短小节问题。

如果一个 subsection 已超过上下文预算，程序会停止并要求按论证重新划分，不会静默截掉后半部分。跨 subsection 的合并应先建立旧内容到新结构的映射；当前脚本不会自动执行合并。

## 四、如何填写小节设计

每个核心单元应有以下内容：

```json
{
  "id": "unit_002",
  "heading": "现有 LaTeX 小节标题，由初始化写入",
  "source_sha256": "初始化记录的小节哈希",
  "kind": "core",
  "question": "网络学习变化参数，相比重新估计常参数究竟增加了什么？",
  "thesis": "收益应按预测任务和参数变化的验证条件解释，不能仅凭拟合误差归因于架构。",
  "comparison_axes": ["learned_component", "conditioning_inputs", "validation_split", "baseline_tuning"],
  "study_keys": ["使用本稿真实引用键，不要照抄此示例"],
  "paragraph_plan": [
    {"role": "problem", "point": "区分重新标定与学习条件依赖关系", "study_keys": []},
    {"role": "comparison", "point": "比较实际学习对象和预测时信息", "study_keys": []},
    {"role": "validation", "point": "检验对照和留出条件能排除哪些替代解释", "study_keys": []},
    {"role": "synthesis", "point": "给出可支持的使用边界和未解决问题", "study_keys": []}
  ],
  "synthesis_claim": "依据完成后的文献比较填写，而不是预先宣布所有研究都支持同一结论。",
  "limitations": "明确哪些比较因数据、任务、来源或验证差异不能成立。",
  "open_question": "提出能够区分两种解释的研究问题。",
  "sparse_evidence_reason": "仅有一篇合适研究时，记录检索范围和保留该小节的理由。",
  "merge_proposal": "若小节没有独立问题，记录应合并到哪一节及内容去向。"
}
```

这段是填写说明，不是可直接通过的真实计划。`study_keys` 应换成本稿真实键；段落的来源分工也应随证据补齐。

短过渡用 `kind: bridge`，并填写 `bridge_reason`。不能为了绕过深度审查，把实质内容全标成过渡。

## 五、研究比较表怎样比原证据库更深入

`evidence_ledger.json` 继续保存窄论断及来源摘录。
`study_comparisons.json` 则回答“读者需要知道哪些研究差异，才能理解本小节”。

每篇记录包含 `citekey`、`source_type` 和 `fields`。`fields` 使用以下字段中与问题有关的项目：

| 字段 | 应提取的具体信息 |
|---|---|
| system_scale | 对象、培养/运行模式、实验或工业尺度 |
| prediction_task | 轨迹重构、预测、改变条件、策略比较或闭环控制 |
| mechanistic_structure | 状态、守恒关系、固定动力学形式和假设 |
| learned_component | 学什么、插在哪个方程或模型层 |
| conditioning_inputs | 网络依据哪些状态、输入、时间或历史信息 |
| observations | 测量手段、采样频率、预处理与测量限制 |
| training_objective | 目标函数、辨识策略、数值处理 |
| constraints | 具体物理约束及其执行方式 |
| sample_size | 独立批次数与重复采样点数，不能混为一谈 |
| validation_split | 时间、整批、反应器、尺度等划分；是否也被用于调参 |
| baseline_tuning | 基线获得了什么数据、标定和优化机会 |
| quantitative_results | 指标定义、任务、单位、对照和不确定性 |
| operating_changes | 实际检验过哪些进料、诱导、尺度或环境变化 |
| uncertainty | 不确定性怎样计算和验证 |
| failure_modes | 实际失败、明确限制、未来工作 |

每个支持性字段使用：

```json
{
  "status": "supported",
  "value": "经原文确认的具体信息",
  "locator": "页码、章节、表或图",
  "excerpt": "实际原文中的短摘录"
}
```

如果 ledger 的短摘录不足以覆盖这些方法细节，可在该研究记录中设置 `source_text_file`，指向工作区内的 UTF-8 原文提取文本，例如 `primary_sources/某篇/source.txt`；对 PDF 先提取文本，不要把二进制 PDF 路径写到这里。
预检会核对摘录是否出现在 ledger 或这个本地文本中。出现匹配不代表语义一定正确，仍需审查位置是否对应、上下文是否改变含义。

状态不能混淆：

- `not_reported`：检查了相关可访问部分，仍未找到；说明检查范围；
- `not_accessible`：拿不到或尚未检查，不得解释成作者没有做；
- `not_applicable`：该维度不适用，说明原因。

全文、部分原文和摘要分别标为 `full_text`、`full_text_excerpt`、`abstract_only`。摘要若明确写出某项详细信息，可标 `explicit_in_abstract: true` 并提供原句；不能只打开该开关却没有实际证据。

## 六、整节审查的五个维度

| 维度 | 通过所需的实质表现 | 常见拒绝原因 |
|---|---|---|
| question_answered | 回答了本节科学问题 | 只解释概念和公式 |
| comparative_synthesis | 研究之间有具体比较关系 | 逐篇排列或堆叠引用 |
| explains_differences | 分析任务、数据、假设或验证怎样影响解释 | 没控制条件却把收益归因于架构 |
| evidence_scope | 表述强度与来源范围相符 | 把摘要、未来工作或模拟说成实证验证 |
| bounded_conclusion | 结论来自比较，且明确适用边界 | 重复定义或只说需要更多研究 |

模型必须为每个维度返回正文中的真实短摘录和具体判断。缺维度、摘录不存在、存在未解决重大问题，都不能把候选稿记为通过。
重大意见使用稳定 ID，后续审查必须提供对应正文与解释才能认定解决；退出程序再重跑也不会清空这些意见。若证据或设计改变，应明确解释旧问题如何被修正或不再适用，不能通过重启流程让问题消失。
这仍然是模型审稿，不能据此宣布专家核验、作者满意或达到期刊录用标准。

## 七、先做样板，怎样开始

1. 在 `synthesis_plan.json` 找到“动力学参数学习与结构化边界”对应的真实单元 ID；若它是某个 subsection 的子标题，会随父小节整体处理。
2. 填写该单元的论证设计和相关研究字段。
3. 将顶层 `sample_unit_id` 设置为该单元 ID。
4. 运行 `audit --unit 实际ID`。逐项补齐，不用捏造研究细节凑通过。
5. 运行 `revise --unit 实际ID`，默认最多三轮。
6. 查看 `synthesis_candidates/实际ID.tex` 及同名 JSON，它们表示最近的生成/审查状态。每轮尝试保存在 `synthesis_candidates/runs/独立运行ID/`，不会覆盖前一次运行；通过模型审查的版本另存到 `synthesis_candidates/accepted/`。审稿接口中断时，新生成的正文仍保留并标为 `review_pending`。
7. 把完整样板、研究比较表、整节审查结果和具体修改说明交给作者阅读。
8. 作者认可 `accepted/` 中这个实际版本后，在 `calibration` 中记录 `approved: true`、`approved_by: user`、样板文本哈希、审查文件哈希和真实偏好。样板与审查报告还必须匹配当前稿件、论证设计、比较表和来源；这些改变后需重新审查校准。填写审批元数据本身不会改变科学内容哈希。

在样板得到实际认可之前，其他单元的批量扩写会被阻止；资料阅读、研究比较、论证设计仍可继续。
作者认可设计方案并不等于认可尚未出现的样板。不要代填“作者满意”。

## 八、怎么判断比旧稿好，而不是更长

作者读完一个核心小节，应能说明：

- 这一节解决的具体问题是什么；
- 哪些研究在何种维度一致或不同；
- 哪种解释受到哪些验证支持，还有哪些替代解释；
- 哪些结论能用于当前任务，哪些不能；
- 下一步最需要区分的科学问题是什么。

如果这些问题仍答不出，增加字数不会解决。应回到研究比较和论证设计，而不是反复让模型“再深入一些”。

## 九、整合与双语稿件

新脚本只生成候选小节，不自动把它们拼成最终全文。整合时应检查跨节重复、术语、比较口径、交叉引用，以及局部结论是否共同支持综述贡献；涉及合并标题时使用明确映射保护原有内容。
英文稳定后再更新中文，避免中文忠实翻译了旧版教材式结构。最后重新编译并检查所有页面。
原稿、当前运行状态、旧分块审查记录都保留；不把技术检查通过当作科学质量通过。
