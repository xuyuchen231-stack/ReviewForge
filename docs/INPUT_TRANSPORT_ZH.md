# 输入压缩验证（2026-10-31）

这次改动只减少重复表头，不筛选、概括或截断科学内容。每项研究的全部字段、原文引句、访问范围、定位、限制和身份仍被传送。比较轴名称与字段列名在请求中声明一次，研究记录按对应列排列。发送前自动反向展开并与原输入逐项比较，不相等就报错。若节省不足 10%，继续使用原格式。

本地证据卡、来源文件、接受标准和契约哈希没有因压缩而改变。现有通过结果不会仅因传输格式更新而被强制重写。写作/审稿的模型、输出上限、深度要求和审稿轮数保持原配置；没有新建整篇夜间任务。

## 测量

- 以当前运行的 49 个已准备证据的单元重建写作输入，逐项展开一致。
- 对比基线已经包含逐字摘录去重与紧凑 JSON，不是对比未经优化的大文件。
- 总输入 UTF-8 字节由 1,173,285 降到 1,093,024，减少 6.84%。12 个单元达到 10% 压缩门槛，其余保持原格式。
- 其中 unit_044 字节减少 21.21%，unit_006 减少 19.32%，unit_029 减少 16.90%。字节减少不是 token 减少。
- 用真实 unit_044 输入在同一 TokenHarbor `deepseek-v4.1-flash:free` 路线上分别核对两种格式，API 报告输入 token 为 16,599 与 13,659，减少 17.71%。两次都准确返回了所选研究字段的状态、结论、定位和逐字引文。
- 该实测是读取保真检查，不是整篇稿件科学质量等价实验，不能把单次 17.71% 推广到所有调用。输出 token 与推理时间也会波动；这次没有通过压缩输出或放宽审稿来换取节省。

私有验证记录保留在本机 `reviewforge-runtime/workspace/study_table_validation/`，不上传其中的稿件与证据。

## 范围与恢复

优化用于 `autonomous_review.py` 的写作/审稿请求，以及独立 `synthesis_pipeline.py revise` 请求。没有更改来源提取的请求结构，也没有假定模型能记住先前请求。新逻辑在下次启动时加载，不对运行中的进程声称热更新。

`RF_STUDY_TABLE_INPUT=0` 可恢复普通研究记录格式。无需换模型、增加账号或使用付费备用平台。发送状态记录包含 `request_table_bytes_saved` 与 `request_input_bytes_saved`，均是请求字节计量，不能充当账单或实际 token 计量。

大量累计 token 还取决于参与的章节数量、证据量及实际修订次数。本改动解决了一部分重复输入，不能据此宣称百万级累计消耗已经整体消失。
